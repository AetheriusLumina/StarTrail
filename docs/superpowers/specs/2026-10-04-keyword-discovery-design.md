# 增长与关键词多来源自动检索设计草案

状态：需求与设计记录，尚未实现。此文件不表示安装包或当前源码已经支持下述行为。

## 目标与已确认范围

1. AI在检索前理解原关键词，补充中英文表达及公开主题，扩大相关项目覆盖。
2. 从GitHub官方搜索、GitHub Trending和Trendshift公开主题/榜单收集候选，合并去重后再交AI判断。
3. 立即更新和定时更新自动触发；每天检查来源和Star变化。不能以“已检查20个”作为每天停止理由，也不能保证全站零遗漏。
4. 每个关键词每次任务最多新增核实200个候选，单批最多20个；有效缓存复用。200是安全上限，不是每天必须凑满的工作量，也不是固定Token预算。
5. 增长模块同样使用多来源发现与AI核对，原增长指标和名额/历史规则不变。
6. 所有交付变化写入统一CHANGELOG与AI_HANDOFF，核验后更新本地活动源码并提交GitHub。

## 数据流

1. 扩词：一次Codex结构化调用，保留原词、最多6个紧密相关的表达；公开主题目录只提供可选标签。验证长度、字符与目录匹配，拒绝AI构造任意请求地址。扩词结果可查看和纠正，按原词、模型与规则版本缓存。扩词调用单列，不能藏在200候选计数里。
2. 采集：统一name/description/README查询范围，按Star和创建日期分区、分页，在时间和请求预算内收集。候选优先存硬盘；以真实repo_id去重，记录各来源及未完成游标。
3. Trendshift：原词和扩展主题与公开目录映射，不再只允许字面完全相同。公开页面后续内容只有在可验证读取方式存在时读取；首屏、未覆盖分页、来源失败分别说明，不伪造全量。
4. 核实：GitHub核实真实仓库状态和Star；分段读取README用途/功能证据。按当前Star优先处理，AI仅判断与原需求是否相关，返回依据与不确定性，不让模型生成Star或排名数字。
5. 缓存：判断指纹包含原词含义/扩词版本、模型、判断规则和仓库语义内容。仅Star变化不重判；新仓库、正文实质变化或规则变化才重新判断。跨日可复用，未入选相关候选保留待用。
6. 选择：合并本组当前候选与已核实相关候选，在最新资格/历史排除/其他组占位约束下，重新按真实Star取前五；使用一致的本组排名，来源顺序单独记录。曾经实际展示的项目需有持久展示记录，不因当日排名替换删除推荐行就丢失排重依据；落选不等于AI判为不相关。仅采集/核实而未展示的项目仍可后续入选。
7. 预译：只准备入选项目所需译文，不给所有候选生成完整AI详情；保留用户手动项目解读的边界。

## 增长模块适配与不变规则

1. 增长模块与关键词模块都使用多来源发现、AI检索规划/证据核对、有限覆盖说明、断点和增量缓存；不只读取Trendshift的关键词首屏。
2. 搜索规划可以提出可执行的GitHub查询与真实公开主题，但原始词、查询范围、仓库和URL均由程序校验。模型记忆中的项目不能直接成为结果，必须获得真实仓库证据。
3. Trending/Trendshift提供项目发现、主题及上榜线索；通过GitHub API补齐仓库身份、归档状态、累计Star和可核实的完整UTC日增。第三方顺序不直接成为产品排名。
4. 关键词模块：AI对原关键词的真实语义做相关性判断；仅偶然提到词、不具备实质相关用途/功能的项目不能因词面匹配入选。程序按当前真实累计Star降序选取合格前五，保持历史排重与其他组占位。
5. 增长模块：AI检查项目证据、源资料与时间口径的矛盾/不足，程序按官方完整UTC日增降序选择。不能让AI生成、补齐或估算日增Star；缺官方记录就保留待核算状态。
6. 原增长规则不变：最近已结束的完整UTC统计日、来源观察时间与保存日期分开、历史前五紧凑展示不占新增五个名额、已展示历史排重、手动更新优先与并发复用。仅同一统计日且日增大于0的真实记录参与排序；日增相同按累计Star降序、再按repo_id稳定排序。
7. 新设计单次新增核实上限200适用于每个关键词或增长任务，每批20；不是整个软件总共200，也不是每次必须跑满。多个关键词和增长一起运行会增加总调用量，界面需分别显示进度与缓存命中，不能隐瞒叠加消耗。
8. 每天重新发现与刷新元数据；普通Star变化不使语义判断失效。增长的逐日数字由程序每日重新核算，不能用昨天数值作今天的证据；身份/语义判断与逐日统计校验缓存分开。
9. 以可能影响最终结果的待核实候选优先：关键词看累计Star前沿，增长看已获得的官方日增前沿。仍有可能进入前列的未判/缺证据候选时，明确部分完成，不写成已经找到全站最佳前五。
10. 原功能、布局、详情手动AI、离线翻译、历史与关注数据及安装身份不因此次适配改变。仅增加自动候选核实并改善候选覆盖/排名。

## 每天更新与费用控制

1. 每天重新扫描配置的检索范围和来源，复核仓库元数据，发现新增、跨门槛及内容变化。
2. 日常核实数量由变化决定，不设置固定20个低上限；单次最多200个。重复操作复用在途任务与有效缓存，不无意义重跑相同批次。同一天更新重新检查来源/元数据，不因已有完成标记跳过；同一日上下文重新选择更优候选，不机械用历史排除把当天本组项目换成下一批。
3. 候选优先级：可能进入前五的高Star未判候选优先；对证据不足候选补读，不把未判断当成不相关。停止后准确保留待核实计数与继续入口。
4. 自动核实状态、额度消耗性质和关闭入口对用户可见。未连接Codex或额度不足保留采集/旧结果，展示原因，不自动登录或无界重试。
5. 对现有已连接、启用关键词的自动核实行为，需要在设置清楚标识。未连接账号不发起付费调用。

## 任务与发布一致性

1. HTTP立即受理，后台阶段为扩词、采集、准备证据、核实、选择/预译、完成/部分完成/暂停/失败/取消；统计原始收集、去重、缓存命中、新核实与待处理数量。
2. 耗时网络与Codex调用不持跨进程更新锁；写入用短事务，检查关键词有效、日上下文、请求代次和取消状态。
3. 手动更新优先于后台AI，重复请求复用；关键词修改、停用、跨日与退出后旧任务不得覆盖新结果。并发任务共享请求预算，不能竞相耗尽GitHub额度。
4. 批次判断先持久化，最后原子发布推荐快照；处理期间旧列表可读，进度变化不反复动画整页。取消后保留已完成判断与待处理游标，但不写入过期快照。
5. 来源失败或预算停止可使用已核实部分，并明确“部分完成”。没有实际覆盖全量分页时不得称“全部检索完成”。每个模块单次任务总时限1800秒，采集阶段最多600秒，沿用Codex单批120秒超时；任一预算先到则保存断点并明确部分完成。GitHub单查询最多返回1000条，超过时按创建日期/Star区间拆分；不把1000设为整个持久候选库的截断上限。以分页流和硬盘队列控制内存，时间/请求预算停止后保留所有已发现候选及游标。使用慢响应回归验证这些边界。

## 当天快照与详情合并修复

1. 已确认缺陷：AI新增推荐会更新repositories和recommendations，但commit_ai_batch未同时保存当天snapshots；详情非历史分支又优先采用任意日期的最新snapshot。因此当天新增推荐可能展示旧Star和旧“本机保存于”。这不等于已证明当天重复推荐，二者需要分别回归。
2. 隔离复现：虚构仓库10月2日快照为1500 Star，10月4日AI新增元数据为2500；现有详情返回10月4日推荐日期、1500 Star与10月2日保存时间，当天快照不存在。未触碰正式用户数据或调用付费AI。
3. 新增推荐、与真实获取时间对应的Star快照及当天上下文原子保存。禁止把旧数值仅改时间冒充实时刷新；来自旧缓存的元数据必须保留观察时间或补取真实新数据。
4. 从当天列表打开详情，使用当天保存上下文，不混入较早或之后的快照；历史页面严格读取对应历史日期，不能被最新元数据覆盖历史数值。
5. 每天重新取得本次范围内的真实元数据，关键词入选排除以前实际展示过的项目、当日其他组已占项目和已归档/低于门槛仓库。当天同一任务重复请求复用，允许更优合格候选替换本组低Star候选，不把替换解释为额外新发现。
6. 没有新增合格项目时显示实际不足；刷新失败时保留旧数据并明确旧日期与失败原因，不把旧卡复制成今天的新卡，也不悄悄改日期。
7. 回归分别覆盖AI新增当天快照、首页/详情一致、历史详情冻结、跨日不重复、仅采集未展示仍可入选、旧缓存时间、同日重复/替换及取消事务完整性。

## 注释、安装包与文件整理

1. 新增/修改的检索、指纹、预算、排名、事务和并发代码写清函数职责、输入输出与关键约束。注释解释为什么这样做，尤其是完整UTC日、历史排重、AI不生成数字、缓存失效、200批次上限及取消后禁止发布，不逐行重复代码。
2. 自动任务调度要覆盖浏览器运行和Windows定时任务入口，不能只改前端按钮。继续使用现有安装/任务身份，避免重复安装或失去旧数据入口。
3. 更新本地活动Repo后运行完整回归、公开文件扫描、源码/文档差异审查，再构建对应源码的新Windows安装包。安装版与源码版本保持一致，旧preview.1不能冒充新功能。
4. 在隔离安装/数据目录验证启动、首次和重复更新、自动流程、无Codex/限流/失败、缓存与译文、升级保留旧数据及退出。可实测的项目完成后记录结果；第二台真实Windows或长期负载未测时如实注明。
5. 更新用户手册、开发指南、AI接续、统一开发日志和双语README；安装包与手册放既有用户交付入口，构建中间文件留忽略目录。
6. 核验后推送GitHub源码并发布对应新Windows预览包，确认实际下载资产/哈希与构建版本一致。普通push/PR仍不得自动发布，使用已经授权的手动构建发布工作流。
7. 旧包、重复验收资料和本次确认为可清理的临时文件整理到既有可删除备份目录，写明来源与保留/删除性质。用户自行删除和卸载，不执行未经要求的卸载。
8. 已安装软件的目录、正式UserData和正在使用的开发环境不移动进备份；旧验收软件在既有卸载入口记录名称/卸载方式，防止移动目录导致卸载器失效。
9. 接续资料合并固定入口，不为同一版本重复创建报告。公共日志只放脱敏工程事实，原始运行日志、个人路径、凭证和数据库留本机。

## 验证与交付

1. 原缺陷回归：低Star旧卡必须可被更高Star、已核实相关且有资格的候选替换；保留历史/其他分组排除。
2. 扩词缓存/校验、跨源去重、主题映射、分页截断/不完整结果、低Star阈值与归档排除。
3. 跨日缓存、仅Star改变、内容改变、模型/规则改变、无指纹旧记录与迁移幂等。
4. 每批20/单次200边界、20之后继续检查、未判高Star和不确定候选、候选不足与有限覆盖状态。
5. 无Codex、额度/超时、源不可用、取消后继续、关键词停用、跨日、更新并发与退出。
6. 全部产品回归、隔离界面、公开文件与Git差异检查；更新集中日志、开发/用户文档，再提交活动Repo和GitHub。新安装包需要独立打包与版本验收，不能仅因推送源码就宣称安装包更新。
